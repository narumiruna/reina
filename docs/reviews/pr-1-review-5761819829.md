## R1 — Issue evidence limits block discovery

- Comment: https://github.com/narumiruna/reina/pull/1#discussion_r4462423923
- Severity: P1. One large issue could repeatedly pause all dispatch and hide later scan pages.
- Evidence: `GitHub.issue` and `readComments` used `GitHubDeferred` for issue evidence limits. `Orchestrator.process` advanced the cursor only after every issue read. `Store.deferDelivery` made that delay global through `Store.blockedUntil`.
- Scope: PR #1 adds these paths. The defect breaks its bounded discovery goal.
- Outcome: Already addressed by this follow-up change.
- Fix: `GitHubIssueDeferred` keeps excessive or changing issue evidence local. Scans log the deferral, process other issues, and advance the page. Issue deliveries do not set a global cooldown. Incomplete evidence is still rejected. Real rate limits retain global backoff.
- Validation: `tests/issue-limits.test.ts` checks comment count, comment bytes, total context bytes, pagination, changed counts, exact accepted bounds, and real rate limits. `tests/orchestrator.test.ts` checks later issues, later pages, unrelated deliveries, and global cooldown for a real rate limit.

## R2 — Rejected writes cannot resume

- Comment: https://github.com/narumiruna/reina/pull/1#discussion_r4462423928
- Severity: P1. A rejected PR creation could occupy the only active job slot until cancellation or expiry. Proposal comments had the same failure.
- Evidence: `Publisher.propose` saved `commentIntent` and its local attempt marker before POST. `Publisher.publish` saved `prIntent` before POST. Both retained intent after explicit rate-limit rejection. Reconciliation then treated an absent resource as an unknown outcome. Store rules correctly prevented intent reversal.
- Scope: PR #1 adds these paths. The defect breaks its durable backoff and idempotent publication goals.
- Outcome: Already addressed by this follow-up change.
- Fix: `GitHubWriteRejected` identifies explicit rate-limited HTTP 403/429 rejection. Optional `commentRetryAt` and `prRetryAt` fields store one retry authorization. The publisher reconciles first and waits until the deadline. It consumes the authorization in durable state before POST. Intent and known identities stay immutable. Ambiguous writes, including HTTP 503 with rate headers, get no retry authorization. Comment retry requires the durable save callback.
- Validation: `tests/github.test.ts` checks both response codes, both resource types, the same or a new publisher, repeated rejection, deadline enforcement, saved consumption before POST, save failures, read deferral, and accepted but hidden retry responses. `tests/core.test.ts` checks SQLite reopen, durable consumption, strict schemas, and immutable intent and resource IDs.

## R3 — Pending delivery can dispatch after shutdown

- Comment: https://github.com/narumiruna/reina/pull/1#discussion_r4462423933
- Severity: P2. A pending read could start a full worker after shutdown began and delay exit.
- Evidence: `stop` aborted only registered controllers. `issue` awaited approval or snapshot reads before it registered a controller. `execute` had no shutdown guard. `Worker.active` could not reject that new, live signal.
- Scope: PR #1 adds these paths. The defect breaks its worker cleanup and shutdown goal.
- Outcome: Already addressed by this follow-up change.
- Fix: A service abort signal reaches active triage and worker signals. Shutdown guards stop late claims, runtime dispatch, and publication recovery. Interrupted dispatch leaves its inbox delivery pending. Assessment is recorded only when triage can start.
- Validation: `tests/orchestrator.test.ts` stops during pending boundary, issue, head, approval, snapshot, and recovery reads. It checks that no new worker or publication starts, then checks safe processing after restart. The existing active-worker shutdown test still passes.
